## Findings

### 1. Jobs: one wide SQLite record mixes Source facts and generated material

Job-ops uses Drizzle with SQLite. Its `jobs` table has a primary ID, tenant/user scope, one `source`, an optional Source external ID, Source URL, direct URL and application link, title/employer/description, location evidence, dates, salary text plus numeric range/currency/interval, remote/workplace information, skills and company metadata. Many Source-specific fields are nullable. [Schema](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/db/schema.ts#L197).

The same row contains lifecycle status, fit score/reason, a structured Job brief stored as text, tailored headline/summary/skills, selected project IDs, PDF path/source/fingerprint/time, and discovery/processing/readiness/application timestamps. Statuses include discovered, processing, ready, applied, in_progress, skipped and expired; uniqueness is scoped to tenant/user and **exact Job URL**, not a cross-Source role identity. [Enrichments and index](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/db/schema.ts#L254).

**Recommendation:** reuse the distinction between original Source facts, normalized facts and AI outputs, but make it explicit in joule’s storage. Store each Job’s Source identity, raw description and normalized compensation/location; store fit assessments separately from typed, versioned Drafts. Avoid making “ready” mean “PDF exists,” because a joule Draft may instead be a Cover Letter or Proposal. This is a proposed adaptation of job-ops’ mixed row to joule’s Job/Draft definitions, not an existing job-ops feature. [Existing fields](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/db/schema.ts#L270), [joule terms](/Users/j/code/joule/GLOSSARY.md:7), [Draft types](/Users/j/code/joule/GLOSSARY.md:23).

### 2. Fit scoring: an LLM rubric, explanation, neutral brief and guarded fact corrections

The default prompt assigns 0–30 points for skills, 0–25 for experience, and 0–15 each for location/remote alignment, domain fit and career growth. User scoring instructions and the Profile are included; this is an LLM-directed rubric, not a deterministic calculation of five separately validated subscores. The response contract asks for one integer score from 0–100 and a brief reason. [Rubric](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/shared/src/prompt-template-definitions.ts#L93), [response schema](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/scorer.ts#L57).

One completion also creates a candidate-independent Job brief with requirements, concrete specifics, employer offerings, practical details, missing information and repeated signals. It proposes whitelisted Job fact patches with confidence and exact description evidence. Instructions explicitly separate fact review and neutral summarization from candidate evaluation. [Contract and instructions](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/scorer.ts#L72), [fact-review instruction](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/scorer.ts#L156).

Patch validation checks shape/field/value, rejects low confidence, requires evidence present in the description, checks that evidence supports the value, and allows medium confidence only to fill missing values. This is stronger than trusting prompt instructions alone, although evidence matching is still a heuristic. [Validator](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/job-fact-patches.ts#L184), [support checks](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/job-fact-patches.ts#L104).

Scoring calls request structured JSON with `maxRetries: 2`; successful numeric scores are rounded/clamped to 0–100. A configurable missing-salary penalty is subtracted in code after accepted fact corrections. Configuration failures and unavailable scoring are distinct exceptions; the Scan scoring step leaves transient failures unscored instead of assigning a poor fit. Existing numeric scores are cached without checking Profile/model/prompt revisions in that cache condition. [Call/validation](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/scorer.ts#L294), [penalty](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/scorer.ts#L230), [cache/failure handling](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/pipeline/steps/score-jobs.ts#L68).

**Recommendation:** implement structured fit score + reason + missing information, explicit failure status, bounded retry and configurable owner preferences. Save model, prompt version, Profile revision and Job-content hash with each assessment so rescoring has a reliable invalidation rule. Keep Source facts immutable and record accepted AI corrections with evidence rather than silently replacing provenance. These are design recommendations motivated by the scoring/cache/patch mechanisms above. [Scoring output](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/scorer.ts#L370), [cache](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/pipeline/steps/score-jobs.ts#L68), [patch output](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/job-fact-patches.ts#L238).

### 3. Tailored CVs: edit limited fields and select existing projects

Tailoring asks for structured `headline`, `summary` and categorized skill keywords from a reduced Profile containing skills, projects and experience. Writing preferences cover language, tone, formality, summary length, keywords per category, additional constraints and avoided terms. The default prompt prohibits invented experience and tells the model to preserve skill levels/categories while renaming/reordering keywords. It also insists on the exact target Job title as the headline. [Schema/call](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/summary.ts#L38), [Profile/style assembly](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/summary.ts#L172), [prompt](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/shared/src/prompt-template-definitions.ts#L55).

Project selection is a separate structured call over eligible project IDs. Unknown/duplicate IDs are rejected and output is capped to the desired count; a keyword-based fallback supplies remaining IDs or handles failure. Orchestration respects mandatory projects, eligible projects and remaining slots, retains valid existing selections, and supports regeneration of selected fields. [Selection and fallback](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/projectSelection.ts#L27), [eligibility/orchestration](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/pipeline/orchestrator.ts#L737).

The CV transformation helpers provide a deep clone, apply tailored headline/summary/skills to structured CV data, and change project visibility. The PDF service prepares tailored data, normalizes it to a renderer document model and invokes either a local renderer or Reactive Resume. This is limited-field tailoring and project selection, not evidence of a complete AI rewrite of every work-history bullet. [Helpers](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/rxresume/tailoring.ts#L23), [visibility](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/rxresume/tailoring.ts#L224), [PDF flow](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/pdf.ts#L343).

**Recommendation:** keep the base Profile immutable and make a Tailored CV Draft a set of approved edits plus selected Profile-item IDs. Validate all IDs and retain stable employment facts. Preserve owner edits during regeneration. Treat the prompt’s exact-title/“#1 ATS factor” language as an unverified claim, not evidence of effectiveness; choose a truthful headline policy instead. Prompt constraints do not establish factual grounding: successful tailoring currently warns on missing fields and fills defaults rather than proving every generated assertion. [Prompt claims](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/shared/src/prompt-template-definitions.ts#L55), [basic validation](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/summary.ts#L116), [field preservation](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/pipeline/orchestrator.ts#L737).

### 4. Typst: local compiler behind a structured document boundary

The local renderer has named theme manifests with native/adapted kinds, a validated entrypoint path and native style tokens. Native themes build Typst source from normalized document fields; text escapes Typst metacharacters and supports a limited bold/italic conversion. Adapted themes use converted fields and a JSON data file. [Manifest validation](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/resume-renderer/typst.ts#L95), [escaping](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/resume-renderer/typst.ts#L201), [render paths](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/resume-renderer/typst.ts#L732).

Rendering creates a temporary directory, writes `resume.typ` and `resume-data.json`, spawns `typst compile` with argument arrays and a 120-second kill timeout, copies the successful PDF and cleans up the directory. `TYPST_BIN` can override the binary. The Dockerfile downloads pinned Typst 0.14.2 for amd64/arm64 and copies the binary into the production image. [Subprocess](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/resume-renderer/typst.ts#L619), [temporary files](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/resume-renderer/typst.ts#L720), [cleanup](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/resume-renderer/typst.ts#L799), [container](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/Dockerfile#L215).

**Recommendation:** use a small original Typst template that reads joule’s own CV JSON and treats generated strings as text, with one pinned compiler/font bundle in the container. Borrow the data/render separation, timeout and cleanup pattern. Typst officially supports JSON loading, and its compiler has an Apache-2.0 licence independent of job-ops’ wrapper/templates. [Typst JSON documentation](https://typst.app/docs/reference/data-loading/json/), [compiler licence](https://github.com/typst/typst/blob/main/LICENSE). Audit any chosen template separately: job-ops’ adapted `clean-print-cv` theme imports `@preview/clean-print-cv:0.1.0` and evaluates converted strings as markup, adding package/network and escaping concerns; do not assume “local compiler” implies a fully offline render. [Adapted theme](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/resume-renderer/typst-themes/clean-print-cv/main.typ#L1).

### 5. Cover Letters: a Ghostwriter use case, not a dedicated generation pipeline

First-party docs identify Cover Letter/outreach drafting as a use case of per-Job Ghostwriter chat: enter a prompt, stream a response, copy it, stop or regenerate. The inspected implementation uses a generic response-string schema, rather than a Cover Letter-specific structured contract. [Docs](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/docs-site/docs/features/ghostwriter.md#L24), [response schema](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/ghostwriter.ts#L72).

Its context builder includes Job facts/description and current tailored fields, a reduced Profile snapshot, writing preferences, and explicitly selected notes/emails/documents. Conversation assembly follows the active branch, excludes failed messages and retains the last 40 messages. Docs describe read-only assistant behavior and note that avoided terms are prompt guidance, not a hard output filter. [Job/Profile snapshots](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/ghostwriter-context.ts#L97), [selected context](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/ghostwriter-context.ts#L404), [conversation](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/ghostwriter.ts#L116), [docs](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/docs-site/docs/features/ghostwriter.md#L77).

**Recommendation:** reuse bounded, explicit context selection and style preferences in original generation code. Start joule with an on-request Cover Letter Draft endpoint and a separate Proposal contract containing cover text plus screening-question answers; chat branches, email integrations and interview preparation can wait. Job-ops’ normal processing pipeline generates CV PDFs for selected scored Jobs automatically, which should not become joule’s Scan behavior. [Pipeline](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/pipeline/steps/process-jobs.ts#L19), [processJob](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/pipeline/orchestrator.ts#L1072), [joule Draft/Proposal definitions](/Users/j/code/joule/GLOSSARY.md:23).

### 6. Dedupe: batch fuzzy merge, persistent exact URL checks, and application-history hints

Before importing discovered Jobs, job-ops fuzzy-deduplicates the current batch. It lowercases/removes punctuation/normalizes whitespace, strips company suffix tokens, then uses a substring length ratio or normalized Levenshtein similarity. A match needs title similarity **strictly greater than 90** and employer similarity **strictly greater than 85**. [Import](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/pipeline/steps/import-jobs.ts#L14), [normalization/similarity](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/shared/src/job-matching.ts#L10), [thresholds and comparison](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/shared/src/job-matching.ts#L285).

Matching Jobs are merged: required Source/title/employer/URL come from the first Job, and optional fields take the first non-null value. Matching compares only title and employer; there is no location, requisition ID or posting-date check in this routine. Thus provenance from later Sources is discarded and order affects conflicts; distinct same-title roles in different locations can be merged. These are deductions from the merge/comparison code, not measured error rates. [Merge](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/shared/src/job-matching.ts#L218), [comparison](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/shared/src/job-matching.ts#L304).

Persistent import skips known **exact** URLs and relies on a scoped unique index for races; existing duplicates are not refreshed by that bulk-import path. A separate Source+external-ID lookup exists, but `createJobs` does not call it. The reviewed import therefore does not establish general fuzzy matching against all previously stored Jobs. [Repository lookup](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/repositories/jobs.ts#L429), [bulk import](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/repositories/jobs.ts#L550), [index](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/db/schema.ts#L300).

A separate application-history matcher attaches a possible duplicate against applied/in_progress Jobs: both title/employer scores must exceed 90, and the new Job must have been discovered within 30 days after the earlier application. This returns a match annotation rather than merging records. [History matching](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/applied-duplicate-matching.ts#L13), [annotation](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/orchestrator/src/server/services/applied-duplicate-matching.ts#L150).

**Recommendation:** make repeated Scans idempotent using `(Source, external ID)` where available, plus conservatively normalized Source URLs. Preserve one Job per Source and link possible equivalents with confidence/evidence; use location/date/requisition/client identity to avoid false positives. Fuzzy title/employer matching is a candidate generator, not sufficient identity proof, especially for Upwork. This avoids the provenance loss above while honoring joule’s existing Job definition. [Current loss mechanism](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/shared/src/job-matching.ts#L223), [joule definition](/Users/j/code/joule/GLOSSARY.md:7).

### 7. Licence: public availability is not permission to copy under joule’s chosen terms

The checked-out licence declares JobOps under AGPLv3 subject to Commons Clause. The clause excludes supplying third parties, for fees or other consideration, a product/service whose value derives entirely or substantially from the software; its definition explicitly includes hosting and related consulting/support. Required licence/attribution notices must include the clause. The README states self-hosting/use/modification are allowed but selling the software or substantially derived paid hosting is not. [Actual grant](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/LICENSE#L1), [maintainer interpretation](https://github.com/DaKheera47/job-ops/blob/cb8803c0566a1d8ec789f1f1ecf121f58ac8b769/README.md#L195). Commons Clause’s own FAQ calls the combination source-available rather than open source. [Official FAQ](https://commonsclause.com/).
