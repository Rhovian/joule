# ADR-0002: Pipeline current state and retained Move history

Accepted: 2026-11-12. Issue #135; stage names, Closed reasons and manual/auto provenance follow the lead's operator-delegated ruling.

`jobs.state = applied` remains the membership flag used by Triage and Telegram. Pipeline adds `pipeline_moves` snapshots and a `pipeline` row pointing at the first and current Move. Stage, Closed reason, next date, provenance and note live in the Move snapshot, with a UTC creation date; there is no duplicated mutable stage column or replay mechanism.

An idempotently installed `AFTER UPDATE OF state` trigger deletes the current pointer whenever a Job leaves applied, in the same transaction as any state writer (including queue and bulk updates). Explicit helper calls only create Applied entries. Telegram's provisional applied flag reserves an in-flight Upwork Send; it creates a manual Applied Move only on successful submission, before notifying Telegram. Failed Send restores the flag and does not manufacture a Pipeline entry. This preserves ADR-0001's manual-applied invariant; no new auto-apply or auto-close behaviour is introduced.

Stage/date/note changes append a snapshot and advance the current pointer under a SQLite write transaction. Repeating an unchanged Stage/Closed reason/date without a note is a no-op. Selecting a Stage clears the Closed reason unless one is explicitly supplied. Closing retains the last Stage and applied flag. Updating or clearing the next date preserves Stage and Closed reason; dates are UTC and clearing one clears its label.

Unmarking applied deletes only the current Pipeline pointer row. History remains in `pipeline_moves` but is absent from the API when the Job is outside Pipeline. Re-applying starts a new Applied Move and first-history pointer; earlier history remains retained and hidden. No purge or history-edit API is introduced.

Startup follows the existing transactional `init_db` migration pattern. Already-applied Primary Jobs without a Pipeline entry get one auto Applied Move, using migration time: the previous schema has no application timestamp. Existing applied entries, including closed ones, are not reset. Unmarked Jobs and Duplicates are not backfilled. Repeated startup adds nothing.

The API accepts manual or auto provenance for future system callers. Issue #138 adds No reply auto-close at Applied: settings-driven 14-day follow-up / 21-day close thresholds use the current application date and exclude any history reaching Screen+ or any prior closure. Startup, the existing 60-second server tick, and Pipeline reads first evaluate without a write lock, acquiring and rechecking under the manual-Move lock only when a closure is due. Evaluation/settings errors are logged and Pipeline reads return the existing state; evaluation failure also leaves the retention purge running. A future Next date suspends both actions until it has passed. Closure appends an auto Move and retains history and next date. Any prior closure, manual or auto, exempts the application from follow-up and auto-close, so reopening stays open; re-application starts a fresh eligibility window. Follow-up Drafts never send messages. Mail integration and follow-up notifications remain out of scope.
