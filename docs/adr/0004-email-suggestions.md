# ADR-0004: Read-only mail and Pipeline email updates

Accepted: 2026-11-12. Issue #140 extends ADR-0003's connection-only boundary.

Use the existing TLS IMAP session and structured AI transport. Account/folder cursors in SQLite track UIDVALIDITY, last UID and last check attempt. A server task evaluates the stored interval every minute, including startup; null means a completed Scan signals the background loop, after Scan cleanup and alerts; cancelled Scans do not. Checks never hold Scan busy. Attempt time is persisted before network I/O so failures respect the interval. Invalid classifier output stores only a failed dedupe key and continues. Transient AI errors retain the cursor behind the first such message for retry at the next interval, while later messages can still produce updates and deduplicate on retry; transport failure keeps the UID cursor for the next due attempt. Authentication failure reusing saved credentials pauses checks until a successful connection save clears expiration; transport errors do not expire credentials. Unexpected errors are logged without remote exception text and do not end the loop.

Only unique deterministic matches to current Pipeline Jobs are retained. Match sender domains against company names and stored Job/application hosts; shared ATS domains require the company name in subject/quote. Source-labelled link hosts derive from the supported Source vocabulary and stored Job links, so board newsletters cannot match their own postings; system-provider subdomains are excluded; employer no-reply addresses remain eligible. For multiple company candidates, subject/quote plus the existing ephemeral body excerpt (at most 4,000 characters) may select a uniquely supported full role title, normalizing punctuation and common title abbreviations such as Sr./Senior. Missing or multiple supported titles remain ambiguous and are discarded; timestamps and candidate order never break ties. Automatic rejection requires a unique company/domain match without title disambiguation: a role mentioned in the body may be an alternative application. This also guards legacy pending rejections. Unique company matches are unchanged. The body excerpt is not persisted. This deliberately favours missing updates over attaching mail to the wrong Job.

Fetch at most the first 16 KiB of each new message using BODY.PEEK, parse with stdlib email, and pass at most 4,000 body characters to one structured classifier. Bodies/attachments and unmatched messages are never persisted or logged. Retain sender name/address, subject, first non-quoted body line (140 chars), date, Message-ID, folder/UID, matched Job/current application, classification and resolution. Missing Message-ID uses a folder/UIDVALIDITY/UID identity. Application acknowledgements are retained as informational “Application received” email updates for the current application and count as emails on its Job card. They never create a Move or change Stage. There is no email rail or email action UI. For classifier none/failed outcomes, retain only account, Message-ID, Job and outcome in a separate dedupe table, with no sender, subject, quote or application data and no card count. HTML head/style/script/blockquote blocks are discarded before extracting text. Mail metadata is not rendered as HTML.

Operator amendment (2026-11-25) supersedes the confirmation policies in this ADR and ADR-0003: remove all email suggestion/confirmation actions, without relocating controls or restoring the rail. The classifier supports only rejection, application received and none; other Stage/date messages produce only ignored dedupe keys. Unambiguous company-matched rejections append an auto Move naming sender/subject, atomically resolving the retained email row. Startup/ticks reconcile existing pending rows before schedule/authentication guards: valid unambiguous rejections apply; uncertain/ambiguous, stale, inactive, re-applied, closed and non-rejection rows resolve ignored with every stored metadata field retained. New acknowledgements are stored as informational resolved records. No email remains awaiting confirmation. Ignored and historical confirmed/excluded records are not re-applied; existing exclusions still suppress redelivery. The legacy table/state names remain for storage compatibility, with confirmed meaning applied and ignored meaning retained without a Move. The suggestions GET and confirm/exclude/ignore POST endpoints are removed.

Reconnection preserves history/exclusions; changing host/user retains the old account's rows until Disconnect, but the new account cannot see or act on them. Disconnect purges all stored email records, exclusions, dedupe keys and cursors along with credentials. In-flight checks discard results if the saved connection changed or was disconnected. Card email counts belong to the current application only and exclude historical exclusions. Duplicate delivery/retries add no Move. Rejections retain Stage and next date; no other email changes Pipeline. No email is sent, marked Seen, deleted or otherwise changed.

Acknowledgements previously classified as none cannot be recovered automatically: only their ignored dedupe keys remain, and advanced UID cursors plus deduplication prevent automatic reconsideration. This change does not reset cursors or reclassify those keys.
